# 异步快速开始

`com.fang.framework.async` 的用法与口径。为什么独立成包、为什么不继承核心 `Scope`，见 §一。

## 一、和核心包什么关系

| | 核心包 | 异步包 |
| --- | --- | --- |
| 类 | `Scope` / `Service` / `Controller<,>` | `AsyncScope` / `AsyncService` / `AsyncController<,>` |
| 初始化 | `public virtual void OnInit()`，同步 | `public UniTask InitAsync()`，**真异步** |
| 释放 | `public virtual void OnDispose()` | `public UniTask DisposeAsync()` |
| 第三方依赖 | **零** | `com.cysharp.unitask` `2.5.11` |
| 依赖方向 | 不引用任何扩展包 | **单向**引用核心包（只读复用 `Data<TConfig>` / `ConfigDataSo` / `ITickable`） |
| 自毁物体 | **不销毁任何 GameObject** | **销毁自己的物体**（父自毁连子物体一起带走） |

**两个族完全独立、不继承、不混用：一棵 scope 树要么整棵同步族、要么整棵异步族。**

为什么不继承：核心的 `Service.Inject(Scope)` 把服务绑死在核心 `Scope` 类型上，`AsyncScope` 不是 `Scope`，所以「父子 + 服务 + 注入 + 向上查找 + tick 递归」这一套只能异步族自己一份（约 150~200 行）。换来的是核心包**仍然零第三方依赖**（`AI约束.md` 第 1 条不修订）。

### 什么时候用异步族

- 初始化里要 `await` **真异步**：加载资产、读文件、网络、寻路 / 烘焙。
- 要**进度条 / 加载画面**：异步族带 `InitProgress` 与 3 个事件，任意 `IAsyncLifecycle` 都读得到。
- 初始化时机由游戏逻辑决定：后建的子、按需建的子系统。

纯同步的装配（建几个服务、连几条引用）留在核心同步族更省事。

## 二、接口与基类

```csharp
public interface IAsyncLifecycle
{
    bool  IsInitialized  { get; }   // 完成（释放后回 false）
    bool  IsInitializing { get; }   // 进行中；未开始 false、释放后 false
    float InitProgress   { get; }   // 0..1

    UniTask InitAsync();            // 协议：框架与调用方调
    UniTask DisposeAsync();
}

public interface IAsyncInjectable    // 可选：实现了才会拿到 Scope
{
    void Inject(AsyncScope scope);
}
```

`AsyncLifecycleBehaviour : MonoBehaviour, IAsyncLifecycle` 是**状态机唯一的一份实现**，`AsyncScope` / `AsyncService` / `AsyncController<,>` 都继承它：

| 成员 | 说明 |
| --- | --- |
| `InitAsync()` | 幂等入口（`virtual`），返回 `Initialization` 句柄 |
| `DisposeAsync()` | 幂等入口，返回 `Disposal` 句柄；**没初始化过就是 no-op** |
| `Initialization` / `Disposal` | 只读句柄，供 `await` |
| `IsInitialized` / `IsInitializing` / `InitProgress` | 三个状态 |
| `ReportInitProgress(float)` | 实现方自己报进度（`Clamp01`；值没变不发事件）。**不在接口上** |
| `InitStarted` / `InitProgressChanged` / `InitCompleted` | 3 个事件，**只报本层、不冒泡**，释放时自动解绑 |
| `protected virtual UniTask OnInitAsync()` | **子类唯一要写的初始化钩子** |
| `protected virtual UniTask OnDisposeAsync()` | 子类释放钩子 |

**协议与钩子分开**：`InitAsync` / `DisposeAsync` 是给框架与调用方的，子类不 override 它们（只有 `AsyncController` 为了收数据 override 一次无参入口）；子类只写 `OnInitAsync` / `OnDisposeAsync`。

**收集类型是接口**：`AsyncScope.Services` 是 `IReadOnlyList<IAsyncLifecycle>`、`AddService<T>() where T : MonoBehaviour, IAsyncLifecycle`。所以「已经继承了别的基类的脚本」不换基类也能当异步服务（见 §3.2），`AsyncService` / `AsyncController` 只是便利基类。

## 三、转换对照

### 3.1 服务：换基类（推荐）

```csharp
// 核心包（同步）
public sealed class AudioService : Service
{
    public override void OnInit()
    {
        LoadBank();
    }
}

// 异步包
public sealed class AudioService : AsyncService
{
    protected override async UniTask OnInitAsync()
    {
        await LoadBankAsync();
    }
}
```

### 3.2 服务：不换基类

```csharp
public sealed class AudioService : MyOwnBase, IAsyncLifecycle, IAsyncInjectable
{
    private readonly UniTaskCompletionSource _source = new UniTaskCompletionSource();

    private AsyncScope _scope;

    public bool  IsInitialized  { get; private set; }
    public bool  IsInitializing => !IsInitialized;
    public float InitProgress   { get; private set; }
    public UniTask Initialization => _source.Task;

    public void Inject(AsyncScope scope)
    {
        _scope = scope;
    }

    public async UniTask InitAsync()
    {
        await LoadBankAsync();
        InitProgress = 1f;
        IsInitialized = true;
        _source.TrySetResult();
    }

    public UniTask DisposeAsync()
    {
        return UniTask.CompletedTask;
    }
}
```

代价（认下）：接口带状态，所以这条路要自己实现三个状态属性 + 幂等 + 完成源。仍然做得到，换来的是「拿到任意 `IAsyncLifecycle` 就能读进度」。

### 3.3 控制器：数据并进入口

```csharp
public sealed class HeroController : AsyncController<HeroConfigDataSo, HeroData>
{
    protected override async UniTask OnInitAsync()
    {
        await LoadModelAsync(Data.Config);
    }
}

// 使用方：数据跟着入口给
var hero = AddService<HeroController>();
await hero.InitAsync(new HeroData(config));
```

- `InitAsync(TData data)` 是**唯一公开入口**，`Data` 严格**只写一次**（第二次给不同实例抛 `InvalidOperationException`）。
- 参数less 的 `InitAsync()` 是 **`override`**：`Data` 还是 null 就抛 —— 框架走接口也走这条，所以「忘了给数据」不会静默。

## 四、语义表

| 状态 | `IsInitialized` | `IsInitializing` | `InitProgress` | 事件 | `await InitAsync()` |
| --- | --- | --- | --- | --- | --- |
| 未 `InitAsync` | false | false | 0 | 无 | 立刻完成 |
| 进行中 | false | true | 0 → 1 | `InitStarted` ×1、`InitProgressChanged` 每次变化 | 挂起 |
| 完成 | true | false | 1 | `InitCompleted` ×1 | 完成 |
| 失败 | false | true | 停在当时值 | 无 `InitCompleted` | **抛原异常** |
| 未完成时被释放 | false | true | 停在当时值 | 无 | 抛取消（`OperationCanceledException`） |
| 已释放（释放前已完成） | false | false | 停在当时值 | 无 | 已完成 |

- 失败就让 `OnInitAsync` 抛出去，异常经 `Initialization` / `await InitAsync()` **原样**传播。**没有** `MarkInitialized` / `FailInitialization`。
- `InitAsync` **幂等**：重复调拿到同一个 `Initialization`。不支持重载 —— 一个 scope 只初始化一次。
- **重入安全**：实现是「先挂句柄、再启动」，所以钩子内部再调 `InitAsync()` 拿到的也是真句柄，不会是「假的已完成」。
- `InitProgress` 是**本层自己设的值，不跨层聚合**：父要展示子树的进度，得自己读子的 `InitProgress` 折算（见 §五 末尾）。
- **释放后事件自动解绑**：`DisposeAsync()` 完成时把 `InitStarted` / `InitProgressChanged` / `InitCompleted` 置空。

## 五、`AsyncScope` 机制

| 项 | 规则 |
| --- | --- |
| `Name` | `GetType().Name`；子物体名 = 类型名 |
| `Parent` / `Children` | 父 → 子**单向**；子不回手掏父 |
| `Services` | `IReadOnlyList<IAsyncLifecycle>` |
| `CreateChildScope<T>()` | 建子物体 + 挂父 + 登记，**不启动** |
| `RemoveChild<T>()` | 摘登记 → 起过就 `await` 其 `DisposeAsync()`；**没起过就直接销毁它的物体**。返回 `UniTask` |
| `AddService<T>()` | 建物体（挂到 `Services` 节点下）→ 是 `IAsyncInjectable` 就 `Inject` → 登记 → **启动它的 `InitAsync()`** |
| `RemoveService<T>()` | 注销 + 释放，**不销毁物体**。返回 `UniTask` |
| `GetService<T>()` | 本层线性扫描 → 沿 `Parent` 一路向上 → 到顶抛 `InvalidOperationException` |
| `AddService` 守卫 | 类型是 `AsyncScope` 时抛 `ArgumentException`（scope 不能当服务登记） |
| `Tick` / `FixedTick` | 先本层 `ITickable` / `IFixedTickable` 服务，再递归子（复用核心的两个接口） |
| 自毁 | `DisposeAsync()` 最后**销毁自身物体**（`isPlaying ? Destroy : DestroyImmediate`） |

`CreateChildScope` / `RemoveChild` / `AddService` / `RemoveService` 都是 `protected`：装配由具体 scope 子类做，外部只能 `GetService<T>()` 取用。

**父怎么折算子树进度**：框架不做聚合，父自己写。样例 `InitDriver` 的写法是「挂一个 `AsyncService` + 核心 `ITickable`，每帧把本层的服务与子 scope 等权折算，再 `ReportInitProgress` 报给本层」——串行 / 并行 / 权重都是游戏逻辑。

## 六、两条刻意不对称的级联口径

| | 初始化 | 释放 |
| --- | --- | --- |
| 是否级联 | **不级联** | **自动级联** |
| 写法 | 父在自己的 `OnInitAsync()` 里显式 `await child.InitAsync()` | 父的 `DisposeAsync()` 内部先逐个 `await` 完子树、再释放本层服务、最后自毁 |

- **初始化不级联**：级联只对「父的钩子里建的子」有效，而后建的子（按钮点出来的下一个界面 / 关卡）只能由游戏逻辑显式 `await`；且串行 / 并行 / 进度怎么折算都是游戏逻辑。
- **释放必须级联**：父自毁会连子物体一起销毁，不先把子树逐个 `await` 完，子的服务永不释放、子的 `await` 方永远挂住。
- 顺序固定 **先子树、后本层服务**；两张表在第一个 `await` 之前就清掉（挂起期间 `Tick` 看不到残留）。
- 子树里没人异步时，`DisposeAsync()` 返回的就是一个已完成 `UniTask`，同步场景的行为与同步族一致。

## 七、四个坑

### 7.1 释放途中会取消未完成的初始化

释放一开始就 `TrySetCanceled()` 掉那个未完成的 `Initialization`，所以 `await InitAsync()` 抛 `OperationCanceledException`、**不会挂住**。同时完成回调带守卫：`OnInitAsync` 晚到的完成不会把一个已释放的 scope 重新标成「已初始化」。

### 7.2 「停看旧根、改看新根」的订阅方必须守「过期事件」

框架的字面顺序是：

```text
IsInitialized = true;
_initializationSource.TrySetResult();   // ← await 方在这一行内同步恢复
InitCompleted?.Invoke(this);            // ← 事件在这之后才发
```

UniTask 会在 `TrySetResult()` **内部同步恢复** awaiter，所以「`await scope.InitAsync()` 之后接着跑下一段逻辑」的调用方，可能在 `InitCompleted` 送达**之前**就把状态换掉了（典型：加载画面改看新的根）。**订阅方必须在回调里判断事件带的根是否还是当前根**，否则旧根迟到的 `InitCompleted` 会把新根的进度顶成 100%、并把加载遮罩提前淡出。样例 `Samples~/LoadingTransition` 的 `IsCurrent(root)` 就是这个守卫。

### 7.3 置 1 不发事件

框架在初始化完成时是**直接写 `InitProgress = 1`、不发 `InitProgressChanged`**。所以若某一轮快到没有任何一次 tick 报过进度，订阅方**一个进度事件都收不到**，只有 `InitCompleted`。只靠事件画进度条的消费方要在完成回调里自己补 100%。

### 7.4 移除要走父侧 API

`RemoveChild` / `RemoveService` 都是**先摘登记、再 `await` 释放**。所以要移除某个服务时，用父的 `RemoveService<T>()`（把登记一起摘掉）；直接调 `child.DisposeAsync()` 只释放它自己的子树，父的登记项仍在。

## 八、和事件总线的关系

异步族的 3 个事件是**对象自己的生命周期事件**，给「它所呈现 / 装配的那一方」订阅 —— 这正是核心 `表现层规范.md` §二的口径：状态走 `Data`（读 `InitProgress`），一次性命令走事件，**C# 原生 `event` 就够，框架不提供任何新机制**。

`com.fang.framework.eventbus` 的定位是**跨对象的一次性命令**（发送方**不认识**接收方）。要把「加载完成」广播给存档 / 成就 / 音乐这类接收方未知的系统时才用它：`Scope.GetService<EventBus>().Publish(...)`。

本包**刻意不依赖** eventbus，样例程序集也不引用 `Fang.Framework.EventBus` —— 装异步包不该被迫再装一个包。

## 九、安装

1. `Tools/Fang Framework/Fang Hub` → 侧栏「框架与扩展」→「刷新」→ 选中本包 →「安装」。
2. `dependencies` 里**能写什么**：只写 registry 能回答的「包名 + 版本」。本包写入了 `com.cysharp.unitask` `2.5.11`（OpenUPM 注册表）；**核心包没有写进去** —— 它按 git URL + tag 分发、不在任何 registry 里，UPM 答不出「`com.fang.framework` 的某版本在哪下载」（核心 `扩展包分发.md` 事实 2）。对核心的依赖靠 asmdef 的 `references`（编译期真实生效）+ FangHub「框架与扩展」页的前置检查（核心未装时禁用安装按钮）+ 本包 `README.md` 的声明落地。
3. **核心包本身仍然零第三方依赖** —— 上面这些都是**本包**的依赖，本包的存在不改变核心包那条硬约束（第 1 条不修订）。
4. 核心包 `0.5.3` 起，「框架与扩展」页在安装本包前会检查 UniTask：没装就先补 `package.openupm.com` 注册表并等它解析成功，然后再装依赖与本包；工程里已有**别的** `scopedRegistries` 时页面会中止并给出手动步骤（见核心 `快速开始.md` §二）。
5. 手动装（不用 FangHub）时，`Packages/manifest.json` 需要 scopedRegistries + `"com.cysharp.unitask": "2.5.11"`，步骤与核心包那节一致。
