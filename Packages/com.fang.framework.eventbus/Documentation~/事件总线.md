# 事件总线

`com.fang.framework.eventbus` 的设计理由。

## 一、它解决什么

`架构总览.md` §三 定的规矩：

> 状态走 Data（视觉脚本自己读），**一次性命令走事件**（动画 / 音效 / 特效这类由 Controller 发 C# `event`，视觉脚本订阅）。

核心包明确不提供事件机制（`架构总览.md` §十三「首期不做」），所以「一次性命令」这条路必须由扩展包补上 —— 这就是本包。

典型调用方：`Controller` 校验完、改完 Data、发一条 `DamageDealt`；`AudioService` 与视觉脚本 `XxxVisual` 各自订阅，播自己的音效与特效。发送方不认识接收方。

## 二、为什么是类型安全，而不是弱类型 `object`

弱类型版本长这样：

```csharp
bus.Publish("damage.dealt", payload);
bus.Subscribe("damage.dealt", obj => { var d = (DamageDealt)obj; ... });
```

代价有三条，全部是编译期就能避免的：

1. **字符串是拼写错误的重灾区**，而且编译器不查 —— 改名、重构、大小写不一致都会静默断链。`typeof(T)` 版本改类名时编译器直接把订阅点标红。
2. **载荷要强制转换**，转换失败的时机是运行时。
3. **载荷类型与事件名之间没有约束**，同一个 key 可以被两处塞进不同类型。

`Dictionary<Type, List<Delegate>>` 版本把这三条全部挪到编译期：`Subscribe<DamageDealt>` 的参数类型就是 `Action<DamageDealt>`，`Publish(new DamageDealt(...))` 的参数类型必须匹配，拼错类型名编译不过。

代价（认下）：**没有基类 / 接口分发**。`Publish<Dog>` 不会触发 `Subscribe<Animal>`。这是刻意的 —— 一旦引入多态分发，就要回答「遍历顺序」「重复触发」「显式 opt-in 标记」这些问题，而本包要的是最小可用。需要分组广播时，领域侧自己定义一个 `AnimalEvent` 结构体装一个 `Animal` 字段即可，比引入分发规则便宜。

## 三、为什么 `EventBus : Service`

`EventBus` 不是静态类，也不是单例，而是 `Service`：

- **生命周期跟着 Scope 走。** `Scope.AddService<EventBus>()` 创建它、`Inject(Scope)` 给它、`Scope.OnDispose()` 逆序调它的 `OnDispose()` —— 订阅表随场景 / 局释放自动清空，不需要业务侧记得退订。
- **作用域可控。** 全局一份就挂在 `AppScope`，一局一份就挂在 `GameScope`，战斗内一份就挂在 `BattleScope`。静态类做不到这件事。
- **取用走 `Scope.GetService<EventBus>()`**，与框架其它能力一致，零反射、零服务定位器以外的机制。
- 这也是本包必须依赖核心包的原因 —— 「扩展包引用核心包」的第一个真实案例。

代价：`EventBus` 是 MonoBehaviour（`Service` 的形态），必须有物体承载。由 `Scope.AddService<T>()` 代劳，业务侧不需要关心。

## 四、为什么订阅幂等去重

`Subscribe` 里有一句 `if (!list.Contains(handler))`。

不加这句时，最常见的事故是**重复订阅导致重复回调**：某个服务 `OnInit` 里订阅一次，又在某个「刷新 / 重连」路径里再订阅一次，于是同一个音效播两遍。这类 bug 表现为「偶发双份」，极难定位。

去重的判据是**委托相等**（同一方法 + 同一目标实例），因此：

- `bus.Subscribe(handler)` 两次 → 只回调一次。
- 两个内容相同但实例不同的 lambda（`_ => order.Add("first")` 与 `_ => order.Add("second")`）→ 视为两个订阅者，各自回调。闭包捕获不同，本来就该各算一份。

代价（认下）：**无法故意让同一个委托被调两次**。真需要「同一处理函数按顺序执行两遍」的场景，包一层 lambda 即可，而这比「每次都怀疑是不是订重了」划算。

## 五、为什么 `Publish` 遍历快照

```csharp
var snapshot = list.ToArray();
for (var i = 0; i < snapshot.Length; i++) ((Action<T>)snapshot[i]).Invoke(payload);
```

不遍历快照时，订阅者在回调里 `Subscribe` / `Unsubscribe` 会直接改正在遍历的 `List<Delegate>`，结果是 `InvalidOperationException`（枚举器版本）或**漏掉 / 重复回调**（下标版本）。这是「回调里退订自己」这种常见写法的必然踩坑。

快照的语义是：**一次 `Publish` 的接收者集合在发布开始时确定**。回调中新增的订阅从下一次 `Publish` 开始生效，回调中退订的订阅者本次仍会被调一次（因为已在快照里）。

代价：每次 `Publish` 一次数组分配。事件是「一次性命令」，频率远低于每帧轮询，这个分配可以接受；真要省，可以按类型缓存数组，但那会引入「何时失效」的复杂度 —— 不做。

## 六、主线程限定

与核心包一致（`架构总览.md` §十二「线程」）：不保证线程安全，限定主线程使用。`Publish` 是同步直调，接收者抛异常会直接冒泡到发送方 —— 不做异常吞掉或延迟分发，因为那会让「谁出的错」变得不可见。

## 七、明确不做

- 弱类型 `Publish(object)` / 字符串 key。
- `IDisposable` 订阅句柄（订阅与退订成对写 `Subscribe` / `Unsubscribe` 即可；句柄要引入新的分配与生命周期）。
- 订阅优先级、事件过滤、一次性订阅、异步 / 延迟分发。
- 跨线程分发、事件队列、每帧批量派发。
- 静态单例 `EventBus.Instance`。

## 八、编辑器接入

本包带一个 FangHub 页（`Editor/EventBusPage.cs`，程序集 `Fang.Framework.EventBus.Editor`）：列出运行中每个 `EventBus` 的物体路径、事件类型、订阅者数量与处理函数，用来回答「谁订了 `DamageDealt`」这类问题。页面只读 —— 不订阅、不退订、不发事件。

两个取舍：

1. **不给运行时开只读 API。** 订阅表 `_handlers` 是私有字段，页面走编辑器侧反射读它。理由：`EventBus` 的公开面是「订阅 / 退订 / 发布」三件事；一个只给编辑器看的只读属性会长期挂在运行时 API 上，而它服务不了任何运行时调用方。
2. **不在编辑器里造事件。** 「发布一条测试事件」需要构造载荷，而载荷类型是业务自定义的 —— 通用页面给不出构造方式，只能退化成让用户填 JSON，那是另一个包（序列化 / 配置）的事。

页面所在程序集 `Fang.Framework.EventBus.Editor` 引用 `Fang.Framework.EventBus` 与核心包的两个程序集（`Fang.Framework` / `Fang.Framework.Editor`），`includePlatforms: ["Editor"]`。这是「扩展包引用核心包、核心包永不引用扩展包」的第一个带编辑器页面的例子：核心包不知道 `EventBusPage` 存在，靠 `TypeCache` 扫属性发现。
