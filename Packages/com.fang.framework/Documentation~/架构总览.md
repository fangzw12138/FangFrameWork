# 架构总览

## 一、核心包回答什么

核心包只回答一个问题：**Data 是什么**。

- 身份：`Data<TConfig>.RuntimeId`
- 配置对应关系：`Data<TConfig>.Config`
- 由 config 完全重建：`Data<TConfig>` 只有带参构造，不存在无 config 的中间态

核心包**不回答**「Data 怎么落盘」。

## 二、分层

| 层 | 类型 | 形态 | 职责 |
| --- | --- | --- | --- |
| 配置 | `ConfigDataSo` | ScriptableObject | 只读配置资产。提供 `Id` / `DisplayName` / `Description` |
| 数据 | `Data<TConfig>` | 纯 C# | 唯一真相来源。身份 + 配置引用 + 状态字段 |
| 逻辑 | `Controller<TConfig, TData>` | MonoBehaviour | 状态、规则、输入响应、跨对象协调 |
| 能力 | `Service` | MonoBehaviour | 由 Scope 创建、装配与释放的长期能力 |
| 容器 | `Scope` | MonoBehaviour | 服务表 / 父子树 / 生命周期驱动 / 释放 |
| 表现 | 视觉脚本 `XxxVisual` | 普通 MonoBehaviour | 渲染、动画、视图引用、场景位置。**不进核心包**，见 `表现层规范.md` |

**`Scope` / `Service` / `Controller` 都是 MonoBehaviour；`Data<TConfig>` 是纯 C#，`ConfigDataSo` 是 ScriptableObject。核心包不提供表现层基类。**

## 三、依赖方向

```text
Controller ──→ Data ──→ ConfigDataSo
```

**单向。`Controller` 不认识表现层。**

`Controller` 只存 `Data` 一个字段（`Initialize` 传入），`Config` 沿链路由到 `Data.Config`。

表现层（视觉脚本 `XxxVisual`、视图句柄 `XxxIWO`）不在核心包里，没有基类，也不与 `Controller` 互相持有。这样切的三个理由：

1. **单向才可测** —— `Controller` 不持有表现层，逻辑测试不需要拖着一套表现层跑。
2. **表现可替换** —— 换一套表现（2D / 3D / 特效版）不需要动 `Controller`。
3. **初始化顺序清晰** —— 只有一条「控制器自己建表现」的装配顺序（`Controller.OnInit()` 里 `AddComponent<XxxVisual>()` + `Initialize(this)`），不存在循环。

表现怎么驱动：**状态走 Data**（视觉脚本自己读），**一次性命令走事件**（动画 / 音效 / 特效这类由 Controller 发 C# `event`，视觉脚本订阅）。C# 原生 `event` 就够，框架不提供任何新机制。完整写法见 `表现层规范.md`。

## 四、为什么 `Controller` 是双泛型

`TData : Data<TConfig>` 这条约束必须两个参数才表达得出来：`Controller<TConfig, TData>` 才能同时钉住配置类型与数据类型的对应关系。单参数版（`Controller<TData>`）写不出这条链 —— 这是双泛型唯一但充分的理由，与表现层无关。

代价（认下）：领域侧要写 `Controller<ItemConfigDataSo, ItemData>`，第二个参数蕴含第一个但 C# 反推不出来。

## 五、为什么没有非泛型 `Data`

- 泛型参数强制每个 Data 绑定自己的配置类型，`Config` 零转换。
- 无配置的领域不继承 `Data`，自行定义独立类型。

## 六、为什么没有无参构造

从类型上堵死「先造一个空 Data 再补 config」这条路。存在「无 config 的中间态 Data」时，必然演化出 `ResolveConfig` / `SetConfig` / `Initialize` / 公开可写属性等回绑写法。

代价：Data 子类不能作为 `[SerializeField]` 字段类型（Unity 反序列化需要默认构造）。配置与数据都是运行时对象，不在预制体上直配。

## 七、为什么 `_runtimeId` 与 `_config` 都标 `[NonSerialized]`

- `_runtimeId`：完全重建即新身份，不需要跨存档存活。若参与序列化，预制体多实例反而会共用同一个 id。
- `_config`：配置是资产引用，序列化进存档没有意义。反序列化时它为空，但因为「先解析 config 再完全重建」，构造完成时它必然就位 —— 因此不存在「回绑」需求。

## 八、为什么没有 `ConfigKey`

完全重建模型下 `Config` 一定先于 `Data` 存在，`_configKey` 只是 `Config.Id` 的副本，没有独立价值。

## 九、为什么核心层不含序列化

序列化是**用途**，不是数据本身。一份 Data 会被存档、网络同步、调试打印、回放录制分别序列化，各自要的格式与裁剪策略都不同。基类一旦认识序列化，就等于替所有用途选定了同一种格式。

`Data<TConfig>` 已经具备序列化的全部前提：`[Serializable]`、子类自行声明状态字段、关键引用标 `[NonSerialized]`。**外部序列化器可以直接工作，不需要框架配合任何 API。**

参考实现（Pixel Crushers Save System）就是这么切的：`DataSerializer` 是抽象，`JsonDataSerializer` / `BinaryDataSerializer` 是可替换实现，全都不侵入数据层。

## 十、核心层与扩展包

`Packages/` 下可并列多个包：核心包 + 若干可选扩展包。**只有单向依赖：扩展包引用核心包，核心包永不引用扩展包。**

| 能力 | 归属 |
| --- | --- |
| 序列化抽象（格式可插拔：JSON / 二进制 / 自定义） | 扩展包 |
| 存档驱动（槽位、分段、区块文件、原子写） | 扩展包 |
| `configKey → ConfigDataSo` 解析层 | 扩展包 |
| 事件总线 | 扩展包（`com.fang.framework.eventbus`） |
| 对象池 | 扩展包 |
| 扩展包分发：索引 + FangHub「框架与扩展」页 | 核心包的 Editor 程序集 |

划分纪律：**凡是格式、协议、外部依赖相关的，一律扩展包。**

### 10.1 扩展包怎么分发

同仓 git URL + `?path=` + 每包独立 tag，索引文件放仓库根 `packages.json`，更新检测由 FangHub 里的「框架与扩展」页自己做（Unity 不检测 git 依赖更新）。完整机制、tag 约定、索引格式、其他工程的两种安装方式见 `扩展包分发.md`。

扩展包的编辑器页面（HUD、配置工具、脚手架…）挂在 FangHub 上：`[FangHubPage]` 属性 + `IFangHubPage` 接口，`TypeCache` 自动发现，**扩展包零注册代码**。完整说明见 `FangHub.md`。

依赖只有单向：扩展包引用核心包，核心包永不引用扩展包 —— 因此核心包的 Editor 程序集可以给扩展包做「安装编排」，但核心包不编译任何扩展包代码。

## 十一、生命周期接口

三个接口，钩子一律 `public`（形态 A：裸接口）。

| 接口 | 成员 | 语义 |
| --- | --- | --- |
| `ILifecycle` | `OnInit()` / `OnDispose()` | 初始化与销毁，成对出现。`Scope` / `Service` / `Controller` 的基础对 |
| `ITickable` | `OnTick(float)` | 每帧能力，谁需要谁实现 |
| `IFixedTickable` | `OnFixedTick(float)` | 固定帧能力，谁需要谁实现 |

- `Scope` 实现 `ILifecycle`：`OnInit()` 置 `IsInitialized = true`；`OnDispose()` 逆序释放子 Scope 与服务、清表、断父链，并置 `IsInitialized = false`。两者都是 `virtual` —— 具体 Scope 子类 override `OnInit()` 来装配（`AddService` / `CreateChildScope`），**必须调 `base.OnInit()`**。
- `Service` 与 `Controller` 基类实现 `ILifecycle` 并给空实现；tick 接口由子类按需挂。
- 三个基类**都不定义 Unity 消息方法**（无 `Awake` / `Start` / `Update` / `FixedUpdate` / `OnDestroy`）：生命周期由使用方显式驱动，框架不抢 Unity 回调。
- 认下的代价：钩子是 `public`，外部可以绕过 `Scope` 直接调 `OnInit` / `OnDispose` / `OnTick`。
- `Controller` 的 tick 驱动者未定，取决于「实体挂载」怎么设计 —— 挂起期间它只实现 `ILifecycle`。

## 十二、Scope 语义

| 项 | 规则 |
| --- | --- |
| 形态 | `MonoBehaviour` 抽象类，实现 `ILifecycle`；`Name => GetType().Name` |
| 服务创建 | `AddService<T>()`（`where T : Service`）：建物体（名字 = 类型名）→ 挂到子物体 `Services` 下 → `AddComponent<T>()` → `Inject(this)` → 入表 → `OnInit()` |
| `Services` 节点 | 懒建：第一次 `AddService` 时在 Scope 物体下建名为 `Services` 的物体并缓存 |
| 服务表 | `List<Service>`，顺序 = 添加顺序 |
| 解析 | `GetService<T>()`：本层线性扫描 → 沿 `_parent` 一路向上 → 到顶抛 `InvalidOperationException` |
| 解析粒度 | 只按具体类型；`where T : Service` 让接口传不进来，因此不索引接口 |
| 依赖获取 | 零反射。服务 / 控制器持有 `protected Scope`，直接 `Scope.GetService<T>()` |
| 移除 | `RemoveService<T>()`：`OnDispose()` → 出表。**不销毁物体** |
| 初始化 | `OnInit()` 置 `IsInitialized = true`；`OnDispose()` 置 `false`，并以此为幂等守卫（未初始化时 `OnDispose()` 是 no-op） |
| 就绪门槛 | **无**。`IsInitialized` 只作状态查询，`AddService` / `RemoveService` / `GetService` 都不检查它，也没有 `Build` 阶段 |
| 父子 | 父 `CreateChildScope<T>()` 建子物体（挂在父物体下）+ `AddComponent<T>()`，登记进 `_children`；子反向记 `_parent` |
| 父管控子 | 父 `OnDispose()` 先逆序驱动全部子 `OnDispose()`，再逆序释放自己的服务 |
| 释放 | 幂等；清服务表 → 清子表 → 断父链。**不销毁任何 GameObject** |
| tick 驱动 | `Tick` / `FixedTick`：先自己的服务（`is ITickable` / `is IFixedTickable`，按添加顺序），再递归子 Scope |
| 单例 | **无任何全局静态实例** |
| Unity 接触面 | `Scope` / `Service` / `Controller` 是 MonoBehaviour；`Data` 是纯 C#，`ConfigDataSo` 是 ScriptableObject。视觉脚本 `XxxVisual` 是普通 MonoBehaviour，不进核心包 |
| 驱动 | 框架**不提供**宿主 MonoBehaviour，也不写 `Awake` / `Update` / `OnDestroy`；使用方自己调 `OnInit` / `Tick` / `FixedTick` / `OnDispose` |
| 线程 | 不保证线程安全，限定主线程使用 |
| 反射成本 | 零反射 |

`Scope` 的 `AddService` / `CreateChildScope` / `RemoveService` 是 `protected`：服务由具体 `Scope` 子类装配，外部只能通过 `GetService<T>()` 取用。

## 十三、首期不做

**核心包**首期不做：`Entry` 启动入口、日志抽象、事件总线、资源管理、对象池、配置表加载器、Editor 工作台、脚本模板生成器、场景切换、序列化 / 反序列化 / 存档。

已落地的不在「不做」之列：

- **扩展包分发**：仓库根 `packages.json` 索引 + FangHub 的「框架与扩展」页（`扩展包分发.md`）。
- **FangHub**：编辑器工具枢纽 + 扩展包页面注册机制（`FangHub.md`）。
- **第一个扩展包** `com.fang.framework.eventbus` 0.1.0：类型安全发布订阅（`Packages/com.fang.framework.eventbus/Documentation~/事件总线.md`）。
