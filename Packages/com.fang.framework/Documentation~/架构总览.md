# 架构总览

## 一、核心包回答什么

核心包只回答一个问题：**Data 是什么**。

- 身份：`Data<TConfig>.RuntimeId`
- 配置对应关系：`Data<TConfig>.Config`
- 由 config 完全重建：`Data<TConfig>` 只有带参构造，不存在无 config 的中间态

核心包**不回答**「Data 怎么落盘」。

## 二、分层

| 层 | 类型 | 职责 |
| --- | --- | --- |
| 配置 | `ConfigDataSo` | 只读配置资产。提供 `Id` / `DisplayName` / `Description` |
| 数据 | `Data<TConfig>` | 唯一真相来源。身份 + 配置引用 + 状态字段 |
| 逻辑 | `Controller<TConfig, TData>` | 状态、规则、输入响应、跨对象协调。MonoBehaviour |
| 表现 | `WorldObject<TController, TData, TConfig>` | 渲染、动画、视图引用、场景位置。MonoBehaviour |
| 能力 | `Service` | 由 Scope 创建、装配与释放的长期能力 |
| 容器 | `Scope` | 注册 / 构建 / 解析 / 注入 / 层级 / 释放 |

## 三、依赖方向

```text
WorldObject ──→ Controller ──→ Data ──→ ConfigDataSo
```

**单向。Controller 不认识 WorldObject。**

`WorldObject` 只存 `Controller` 一个字段（`Initialize` 传入），`Data` / `Config` 沿链路由；`Controller` 只存 `Data`。

砍掉 `Controller → WorldObject` 的三个理由：

1. **销毁期悬空** —— 两者挂在同一 GameObject 上，Unity 不保证销毁顺序。一方 `OnDestroy` 里访问另一方，对方可能已销毁。双向依赖时靠人守约定压着，编译器帮不上忙。
2. **初始化循环** —— Controller 要 WO、WO 要 Controller，谁先 `Initialize` 说不清。
3. **测试与替换** —— Controller 逻辑单测得造 WO 实例；想换一套表现就得动 Controller。

砍掉后怎么驱动表现：**状态走 Data**（WorldObject 自己读），**一次性命令走事件**（动画 / 音效 / 特效这类由 Controller 发 C# `event`，WorldObject 订阅）。C# 原生 `event` 就够，框架不提供任何新机制。

## 四、为什么 `Controller` 是双泛型

`WorldObject` 要写 `where TController : Controller<TConfig, TData>` 这条约束，才能沿链路由到 `Data` / `Config`。单参数版（`Controller<TData>`）写不出这条链 —— 这是双泛型唯一但充分的理由。

代价（认下）：领域侧要写 `Controller<ItemConfigDataSo, ItemData>`，第二个参数蕴含第一个但 C# 反推不出来。

## 五、为什么没有非泛型 `Data`

- 泛型参数强制每个 Data 绑定自己的配置类型，`Config` 零转换。
- 无配置的领域不继承 `Data`，自行定义独立类型。

## 六、为什么没有无参构造

从类型上堵死「先造一个空 Data 再补 config」这条路。存在「无 config 的中间态 Data」时，必然演化出 `ResolveConfig` / `SetConfig` / `Initialize` / 公开可写属性等回绑写法。

代价：Data 子类不能作为 `[SerializeField]` 字段类型（Unity 反序列化需要默认构造）。配置与数据都是运行时对象，不在预制体上直配。

## 七、为什么 `_runtimeId` 与 `_config` 都标 `[NonSerialized]`

- `_runtimeId`：完全重建即新身份，不需要跨存档存活。若参与序列化，预制体多实例反而会共用同一个 id。
- `_config`：配置是资产引用，序列化进存档没有意义。反序列化时它为空，但因为「先解析 config 再完全重建」，构造完成时它必然就位 —— 因此不存在「回绑」需求。

## 八、为什么没有 `ConfigKey`

完全重建模型下 `Config` 一定先于 `Data` 存在，`_configKey` 只是 `Config.Id` 的副本，没有独立价值。

## 九、为什么核心层不含序列化

序列化是**用途**，不是数据本身。一份 Data 会被存档、网络同步、调试打印、回放录制分别序列化，各自要的格式与裁剪策略都不同。基类一旦认识序列化，就等于替所有用途选定了同一种格式。

`Data<TConfig>` 已经具备序列化的全部前提：`[Serializable]`、子类自行声明状态字段、关键引用标 `[NonSerialized]`。**外部序列化器可以直接工作，不需要框架配合任何 API。**

参考实现（Pixel Crushers Save System）就是这么切的：`DataSerializer` 是抽象，`JsonDataSerializer` / `BinaryDataSerializer` 是可替换实现，全都不侵入数据层。

## 十、核心层与扩展包

`Packages/` 下可并列多个包：核心包 + 若干可选扩展包。**只有单向依赖：扩展包引用核心包，核心包永不引用扩展包。**

| 能力 | 归属 |
| --- | --- |
| 序列化抽象（格式可插拔：JSON / 二进制 / 自定义） | 扩展包 |
| 存档驱动（槽位、分段、区块文件、原子写） | 扩展包 |
| `configKey → ConfigDataSo` 解析层 | 扩展包 |
| 事件总线 | 扩展包 |
| 对象池 | 扩展包 |

划分纪律：**凡是格式、协议、外部依赖相关的，一律扩展包。**

## 十一、Scope 语义

| 项 | 规则 |
| --- | --- |
| 注册时机 | 仅 `Build()` 之前允许注册；之后注册抛 `ScopeStateException` |
| 生命周期 | 每 Scope 单例。首次创建后复用，不重复构造 |
| 创建时机 | `Build()` 按注册顺序创建全部注册项 → 调用 `Inject` → 调用 `Initialize` |
| 构造函数注入 | 选取 public 构造函数；存在多个时取参数最多的；参数类型递归 `Resolve` |
| 层级解析 | 当前 Scope 注册表未命中 → 向 `Parent` 递归查找 |
| 覆盖 | 子 Scope 的同类型注册遮蔽父 Scope 的注册 |
| 循环检测 | 解析栈检测，命中抛 `ScopeCircularDependencyException`，消息中打印完整链路 |
| 释放顺序 | `Dispose()` 逆序释放已创建实例；`IDisposable` 实例调用 `Dispose()`；子 Scope 需自行释放，父不代管 |
| MonoBehaviour | 无法构造函数注入 → 由 `Inject` / `InjectHierarchy` 显式回调 `IInjectable.Inject` |
| 线程 | 不保证线程安全，限定主线程使用 |
| 反射成本 | 构造函数信息按 `Type` 缓存 |

`Resolve` 要求 Scope 已 `Build`；`Dispose` 之后任何 `Resolve` / `Register` 抛 `ScopeStateException`。`Dispose` 幂等。

## 十二、首期不做

`Entry` 启动入口、日志抽象、事件总线、资源管理、对象池、配置表加载器、Editor 工作台、脚本模板生成器、场景切换、序列化 / 反序列化 / 存档。
